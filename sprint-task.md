Этап 2. Разбиваем проект на микросервисы
Пользователей стало гораздо больше, и нагрузка на сервис ExploreWithMe увеличилась. В числе прочих появились следующие проблемы:
Ограниченная масштабируемость. Монолитная архитектура не позволяет эффективно распределять нагрузку. Например, высокий трафик на функциональность поиска событий может замедлить работу всего приложения.
Сложность изменений. Любая доработка кода может затронуть другие части системы, увеличивая вероятность ошибок. Исправление багов или добавление новой функциональности становится долгим и рискованным процессом.
Снижение надёжности. Если одна часть системы перестаёт работать, это может вывести из строя весь монолит. Например, сбой в управлении заявками на участие может заблокировать доступ ко всему сервису.
Нагрузка на инфраструктуру. С ростом числа пользователей и событий однотипные запросы (например, поиск событий) перегружают серверы. Это приводит к увеличению времени ответа и ухудшению пользовательского опыта.
На втором этапе дипломной работы вы начнёте постепенное преобразование основного монолитного сервиса в набор микросервисов. Это один из важнейших шагов в эволюции проекта, который позволяет улучшить масштабируемость, устойчивость и гибкость системы.
Инфраструктурные компоненты, добавленные вами на предыдущем этапе, — это фундамент для успешного выполнения текущего задания:
API-шлюз. Обеспечивает единый входной API для клиентов, несмотря на изменения в архитектуре. С его помощью запросы будут перенаправляться в соответствующий микросервис.
Сервис конфигурации. Централизованное управление настройками позволит упростить конфигурацию микросервисов.
Сервис обнаружения. Служит связующим звеном между микросервисами, позволяя им регистрироваться и находить друг друга динамически.
Всё это поможет минимизировать риски и упростить разделение основного сервиса.
Что нужно сделать
Определите границы микросервисов. Разделите функциональность основного сервиса на отдельные логические модули: 
управление мероприятиями;
управление заявками на участие;
администрирование пользователями;
дополнительная функциональность.
Перенесите функциональность из монолита в микросервисы. Для каждого микросервиса:  
Создайте модуль в группирующем Maven-модуле core.
Реализуйте функциональность микросервиса для выделенной функции.
Используйте OpenFeign и Eureka для межсервисного взаимодействия.
Используйте ConfigServer для получения конфигурации.
Проверьте работоспособность нового микросервиса.
Настройте маршруты в API-шлюзе для перенаправления запросов на нужный микросервис.
Уберите из main-service реализацию, которая была вынесена в отдельный микросервис.
Как правильно разбить проект на микросервисы
Предлагаем выделять микросервисы постепенно.
Шаг 1. Получаем модульный монолит

Для начала выделите границы каждого сервиса в отдельный Maven-модуль. В полученной структуре main-service будет зависеть от модулей:
управление мероприятиями;
управление заявками на участие;
администрирование пользователями;
дополнительная функциональность;
другие модули.
Итого в основном сервисе практически не останется исходного кода, кроме кода для запуска Spring Boot приложения.

Шаг 2. Разбиваем монолит на микросервисы

Теперь можно начать «отщеплять» каждый модуль от монолита и оформлять в отдельный микросервис. Вот что для этого нужно сделать:
Сделайте модуль Spring Boot приложением и удалите модуль из основного сервиса.
Замените все прямые вызовы зависимостей на запросы через Feign-клиент. Для реализации может потребоваться изменить API модулей. Обратите внимание на следующие пункты: 
Старайтесь расширять и добавлять новые методы, а не удалять и изменять существующие.
Учитывайте количество запросов таким образом, чтобы оно было фиксированным. Так вы сразу решите проблему N+1 запроса.
Поработайте над хранением данных. Подумайте, какие таблицы перенести в сервис и какие данные потребуется добавить или модифицировать в схеме базы данных.

Тестирование
Чтобы клиенты не заметили изменений в приложении и для проверки совместимости, необходимо пройти Postman-тесты — как подготовленные вами для дополнительной функциональности, так и существующие для основного сервиса и статистики. Теперь все запросы тестов должны отправляться к одному приложению через Gateway (порт 8080) и не зависеть от внутреннего устройства приложения.
Надёжность
Перед сдачей работы на проверку проверьте архитектуру приложения на устойчивость к сбоям. Для этого:
Запустите все микросервисы и выполните Postman-тесты.
Начните по одному останавливать микросервисы. Наконец, остановите всё, кроме сервиса мероприятий.
Предполагается, что сервисы продолжат успешно обрабатывать запросы, если они не зависят критически от другого микросервиса. Допустим, если нет данных от сервиса заявок, можно будет по умолчанию вернуть фиксированное значение (например, 0 или 1).
Если возникают ошибки с кодом 5xx, потребуется подключить и настроить Resilience4j и Retry.
